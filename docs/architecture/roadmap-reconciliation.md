# Roadmap Reconciliation

There are three planning documents in play for this project, and each one uses the word "Phase" or a stage label for something different: `realestate-saas-phase1-architecture.md` numbers Phase 0 through Phase 10 for the original property-only build, `marketplace-expansion-audit-and-plan.md` uses P0 through P4 for the cars expansion and everything layered on top of it, and the client's own My Assets, maintenance, documents, expenses, reminders, and service marketplace specification (audited in `asset-platform-implementation-audit.md`, not saved as its own file since it was given inline) has its own internal five phases. This note is the single list that supersedes all three going forward. When talking about "what's next," use the stage numbers here, not "Phase 3," which now means three different things depending on which document someone opens.

## The canonical stage list

**Stage 1, Discovery and architecture.** Original architecture doc's Phase 0 and Phase 1. Done: the architecture document itself, reviewed and approved.

**Stage 2, Design system.** Original architecture doc's Phase 2. Done, and redone once: the first pass was rejected as too generic, the v2 material palette (paper, parchment, ink, bark, clay, patina) and the Libre Caslon Text plus IBM Plex pairing replaced it and is the system in use today.

**Stage 3, Priority 1 property screens.** Not a named phase in either document, the first real build against the v2 design system: homepage, search and results, property detail, agent profile, login, registration, all running on mock data. Done and verified (real build, route smoke test, dash character scan).

**Stage 4, Marketplace expansion foundation.** Expansion plan's P0: Vercel deployment visibility, centralizing the brand name behind configuration, the shared Listing and Location data model, and Ogun State and Abeokuta throughout search, filters, and seed data. Done, shipped as `p0-foundation-update.zip`.

**Stage 5, Cars marketplace.** Expansion plan's P1: the Vehicle data model, vehicle card, search and filters, detail page, dealer role, seed data, and navigation entry, kept deliberately distinct from the property card's information hierarchy rather than a relabeled copy. Done, shipped as `p1-cars-marketplace.zip`, with the last remaining polish item (both galleries now use real seeded photography per image, with an independent fallback to the illustrated treatment if one photo fails to load) finished in this session.

**Stage 6, Current housekeeping.** Not in either prior document, this note plus two small pieces of prep work: this reconciliation, and defining the client's My Assets specification's Phase 2 data shapes (Document, MaintenanceRequest, MaintenanceRecord, Expense, Reminder, Inspection) as TypeScript interfaces only, no UI, so the schema exists before the backend needs to hold it. Done.

**Stage 7, Real accounts and a backend.** Original architecture doc's Phase 3 (Authentication and User Management). This is the fork every later stage depends on: real registration and login, sessions, a database, and ownership relations connecting a user to what belongs to them. Done for what this stage promises: a FastAPI backend (`apps/api`) with a full ORM schema and applied migration for every module in the architecture doc (users, auth, locations, properties and vehicles under the shared Listing model, media, verification, messaging, inspections, reports, notifications, payments, admin), and a real auth flow end to end, argon2id password hashing, JWT access tokens, rotating refresh tokens with reuse detection and family revocation, CSRF defense on cookie authenticated mutations, and per-account and per-IP login rate limiting. `apps/web` is wired to it: registration, login, silent session restore on reload, and sign out all go through the real API rather than simulated state, and the nav, dashboard, messages, and notifications pages honestly branch on whether a session exists. See `README.md` at the repo root for how to run both together locally. What Stage 7 does not include, on purpose: routers for anything past auth and `/users/me` (that is Stage 8 and Stage 10, once the entities those routers serve are what the dashboards actually need), and a production deployment (this is a local scaffold, deployable later).

**Stage 8, Listing creation, dashboards, messaging, and inspections.** Expansion plan's P2, overlapping with the original architecture doc's Phase 4 (property CRUD and media upload), Phase 6 (enquiries, messaging, inspections), and the dashboard structure described in the expansion plan's section 9. Not started, blocked on Stage 7.

**Stage 9, My Assets and the client's asset-platform specification.** The five phase specification audited in `asset-platform-implementation-audit.md`: My Properties, My Cars, documents, maintenance requests and records, expenses, reminders, the service marketplace, and eventually an AI assistant. That specification's own internal Phase 1 through 5 numbering stays as the client wrote it and is referenced as "the My Assets specification's Phase N," never shortened to just "Phase N," to avoid colliding with this list or the architecture document's numbering. Not started, blocked on Stage 7, since none of it can hold real data without accounts.

**Stage 10, Verification and trust expansion, admin, search and map, resident experience and reputation.** Expansion plan's P3, overlapping with the original architecture doc's Phase 7 (verification and trust) and Phase 8 (admin dashboard): the admin interface, the trust and safety surface, map views on search and detail pages, a full accessibility pass, CI, and the resident experience and reputation data model (Tenancy, ResidentExperienceReview, IssueReport, ResidentLifecycleEvent, PropertyReputationSummary) with its structured review flow, seeded only with clearly marked illustrative reviews until real tenancies exist. Not started, mostly blocked on Stage 7; the verification and admin pieces can start once Stage 8's real entities exist to review.

**Stage 11, Resident lifecycle automation.** Expansion plan's P4: the actual move-in, check-in, and move-out notification triggers, landlord and agent responses to reviews, and review-specific moderation rules, running against real Tenancy records. Not started, blocked on Stage 9 and Stage 10 both existing with real data behind them, not just Stage 7.

**Stage 12, Monetization, security hardening, and launch.** Original architecture doc's Phase 9 (monetization, featured listings, payment integration) and Phase 10 (security hardening, testing, production deployment). Not started, and deliberately last: it depends on nearly everything above it existing first.

## The one open decision

Stage 7 is done, which reopens the choice of what comes next. Stage 8 (listing creation, dashboards, messaging, inspections) is the natural next step since it is what the now real accounts are actually for, but Stage 9 (My Assets) and the trust and verification half of Stage 10 are also unblocked now that accounts exist, and could be sequenced first if the client's priorities point that way. This should be an explicit choice made with the client's current priorities in view, not a default.
